JUnit

Tests bisher

  • Ausgaben in der Konsole 
                                    
System.out.println("Ergebnis: " + MeineKlasse.meineMethode(""));
System.out.println("Ergebnis: " + meinObjekt.meineMethode(""));
  • Zahlreiche Nachteile
    • Aufwändig nachzuvollziehen, ob Ausgaben korrekt sind.
    • Tests und Programmcode nicht getrennt.
    • Schwer zu verwalten. Tests sollten nicht im Produktivcode enthalten sein.

Was ist JUnit?

  • Framework zum Testen von Java Programmen
  • JUnit ist nicht Teil vom (Standard-) Java sondern muss extra hinzugefügt werden.
  • Wir verwenden JUnit6 oder JUnit5 (nicht JUnit4)

Was ist JUnit?

  • JUnit ist ein Werkzeug zum automatischen Testen von Java-Code.
  • Ein Test prüft ein erwartetes Verhalten.
  • JUnit meldet, ob die Prüfung bestanden wurde.
  • Test(s) einmal schreiben -> beliebig oft ausführen

Testklasse

  • Eine Gruppe von Tests wird in einer Klasse zusammengefasst.
  • Bei sogenannten "Unit Tests" wird immer eine "Unit" isoliert getestet.
    • Bei uns ist eine "Unit" eine Klasse
    • Eine Testklasse für jede Klasse
  • Namenskonvention für Testklassen: Klassenname + "Test"
    • Beispiel: Klasse "Person" -> Testklasse "PersonTest"
  • Tipp: Testklasse automatisch von IntelliJ generieren lassen

Testmethode

  • Ein Test ist eine Methode, die ein erwartetes Verhalten prüft.
  • Testmethoden müssen mit @Test annotiert werden 
    •                             
                                @Test
public void getFirstName_single(){

}

Assertions

  • Eine Assertion ("Behauptung") ist eine Aussage, die überprüft wird.
  • Vergleich das gewünschte Ergebnis mit dem tatsächlichen Ergebnis.
  • Ist die Bedingung nicht erfüllt, bricht der Test ab und gibt eine entsprechende Fehlermeldung aus.
  • Es stehen verschiedene Assertions zu Verfügung
    • assertEquals(expected, actual, message)
    • assertTrue(condition, message)
    • https://junit.org/junit5/docs/current/api/org.junit.jupiter.api/org/junit/jupiter/api/Assertions.html

Assertions - Beispiel

                        
                            assertEquals("test",  //erwarter Wert
    "TEst".toLowerCase(),	//aktueller Wert - vom zu testenden Code
    "Umwandlung in Kleinbuchstaben nicht korrekt."); //Nachricht (optional)

Beispiel: Testklasse mit 2 Tests

                        
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class CalculatorTest {
    @Test
    void add_twoPositiveNumbers_returnsSum() {
        Calculator calculator = new Calculator();

        int result = calculator.add(3, 5);

        assertEquals(8, result);
    }

    @Test
    void add_twoNegativeNumbers_returnsSum() {
        Calculator calculator = new Calculator();

        int result = calculator.add(-3, -5);

        assertEquals(-8, result);
    }
}

AAA: Der Bauplan für Tests

  1. Arrange: Vorbereiten - Objekte und Eingaben erstellen.
  2. Act: Ausführen - Die zu testende Methode aufrufen.
  3. Assert: Überprüfen - Ist das Ergebnis wie erwartet?

Arrange → Act → Assert

Kannst du die Schritte in den Tests auf der vorherigen Folie erkennen?

Lass die Klasse kurz die drei Teile im vorherigen Beispiel benennen.

Tests verständlich benennen

Ein guter Name sagt: Was passiert, unter welcher Bedingung und mit welchem Ergebnis?

  • Schlecht Namen: test1(), testAdd(), testMethod()
  • Bessere Namen: add_twoPositiveNumbers_returnsSum(), withdraw_insufficientBalance_throwsException(), findUser_unknownId_returnsEmptyOptional()
  • Konvention: method_condition_expectedResult.
  • Sollte einen einheitlichen Standard im Projekt geben.

Wo liegen die Tests?

  • Testcode von Produktivcode trennen
  • Tests in einer separaten Verzeichnisstruktur aufbewahren.

Welche Fälle sollte ich testen?

  • Normalfälle
    • Gültige Eingaben
    • Beispiel Konto: 100 € − 30 € = 70 €
  • Grenzfälle
    • z.B. genau der ganze Betrag
    • 100 € − 100 € = 0 €
  • Fehlerfälle
    • z.B. zu wenig Guthaben
    • 50 € − 80 € → Fehler
  • Ungültige Eingaben
    • z.B. Negativer Abbuchungsbetrag
    • −10 € → je nach Regel ablehnen

Merke: Teste nicht nur, wenn alles glattläuft.

Wenn etwas schiefgehen soll: Exceptions

Mit assertThrows testen wir, ob eine erwartete Exception geworfen wird. 

                        
@Test
void divide_byZero_throwsArithmeticException() {
    Calculator calculator = new Calculator();

    assertThrows(
        ArithmeticException.class,		//erwartete Exception
        () -> calculator.divide(10, 0)	//Funktion, die den Code aufruft, der die Exception werfen soll
    );
}
  • Der Test besteht, wenn die erwartete Exception geworfen wird.
  • Die Klasse braucht dafür eine passende divide-Methode.

Viele Eingaben? Parametrisierte Tests!

Wenn die gleiche Prüfung mit verschiedenen Werten wiederholt wird, hilft @CsvSource. 

                                
                                    @ParameterizedTest
@CsvSource({
    "2, 3, 5",
    "0, 5, 5",
    "-2, 2, 0",
    "-3, -4, -7"
})
void add_differentInputs_returnsExpectedSum(
        int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}

Zusätzlich benötigt: Imports für ParameterizedTest und CsvSource aus JUnit Jupiter.

Erkläre eine Zeile als Eingabe a, Eingabe b und erwartetes Ergebnis. Jede Zeile ist ein eigener Testlauf.

Vorbereitung wiederverwenden

@BeforeEach läuft vor jedem Test und kann gemeinsame Vorbereitung übernehmen. 

                                
class CalculatorTest {
    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();
    }

    @Test
    void add_returnsSum() {
        assertEquals(8, calculator.add(3, 5));
    }
}

Tipp: Nur wirklich gemeinsame Vorbereitung hier ablegen. Besondere Eingaben bleiben am besten im jeweiligen Test.

@BeforeAll, @BeforeEach,...

  • Methoden in der Testklasse können mit weiteren Annotations ausgezeichnet werden.
  • @BeforeAll: Einmal vor allen Tests der Testklasse ausgeführt
  • @BeforeEach: Vor jedem einzelnen Test ausgeführt
  • @AfterAll: Nach allen Tests der Testklasse ausgeführt
  • @AfterEach: Nach jedem einzelnen Test ausgeführt

Gute Tests sind …

  • Unabhängig: Jeder Test kann allein laufen.
  • Verständlich: Name und Aufbau erklären die Prüfung.
  • Gezielt: Ein Test prüft ein konkretes Verhalten.
  • Wiederholbar: Das Ergebnis hängt nicht von Zufall oder Reihenfolge ab.
  • Automatisierbar: Tests können automatisch ausgeführt werden.

Code Coverage

  • Code Coverage (Testabdeckung) bezeichnet das Verhältnis von Code, der durch Tests ausgeführt wird, zum gesamten Code.
  • Code Coverage Report von IntelliJ erstellen lassen.
  • In den Übungen wollen wir 100% Code Coverage.
    • In der Praxis aufgrund von Kosten-Nutzen meist eine etwas geringere Abdeckung

Test Driven Development
(TDD)

Test Driven Development (TDD)

  • Bestimmte Vorgehensweise beim Programmieren (Entwicklungsmethode)
  • Tests werden vor dem Code geschrieben.

Test Driven Development -

TDD im agentischen Development

  • Der Mensch klärt das gewünschte Verhalten und formuliert Beispiele und Grenzfälle.
  • Ein Coding-Agent kann Tests und Implementierung erstellen
  • Dann: Tests bestehen lassen, Änderungen überprüfen und refaktorisieren.

Je schneller Code entsteht, desto wichtiger ist schnelles, verlässliches Feedback.

TDD unterstützt die Kontrolle von generiertem Code, ersetzt sie aber nicht.
